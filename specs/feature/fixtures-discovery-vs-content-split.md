# Feature: fixtures-discovery-vs-content-split

## Git Setup

- Branch: `feat/fixtures-discovery-vs-content-split`
- Base: `main` (7f49d20)

## Feature Brief

Give the skill test suite a **named taxonomy that lives in the
runner**, so what a skill test *is* stops being tacit knowledge spread
across 13 hand-written fixture prompts.

Two things are wrong today. First, every fixture opens by handing the
agent the skill name and its file path, so every fixture answers only
one question — whether the skill *says* the right thing once loaded. A
skill whose `description:` is too weak to auto-trigger passes the whole
suite, because the fixture does the triggering on its behalf. Second,
each fixture hand-copies the per-agent skill paths into its prompt, and
they have already drifted: **six fixtures run against `codex` while
naming only the claude and kiro paths**, so on codex the agent is told
to look in two directories, neither of which is its own skills root.

The fix is a division of labour. A fixture carries only what is
specific to it — which skill, what task, what counts as correct. The
**runner** owns everything general: the per-agent skill roots, the
construction of an *explicit* versus an *implicit* prompt, and the four
kinds of test. Test kinds become executable functions in one file
rather than a convention re-typed per fixture, and `project.md`
narrates the design.

## The taxonomy

Two independent axes, which compose:

- **How the skill is reached** — *explicit* (the prompt names the skill
  and its path) or *implicit* (the prompt states only the task).
- **What is verified** — the skill *plays back* the contract it was
  designed for (recites its rules), or *enacts* it (actually does the
  thing).

| Test kind | Prompt | Verifies | Question it answers |
|---|---|---|---|
| `activation` | explicit | skill announces itself | Is the skill reachable, parseable, and does it load when asked directly? |
| `discovery` | implicit | skill announces itself | Does the skill's own `description:`/trigger fire from a bare task? |
| `playback` | explicit | contract recited | Does the skill correctly state its own rules — guardrails, refusals, absence paths? |
| `enact` | explicit | contract performed | With the skill loaded, does the agent actually produce the artefact or the styled output? |
| `integration` | implicit | contract performed | End-to-end: does the skill fire *and* do the right thing from a bare task? |

`integration` is not a fifth peer — it is the composition
*enact × implicit*, and the spec names it because that end-to-end pair
is the thing worth running.

**The empty cell is deliberate.** The 2×2 leaves *playback × implicit*
— "discover the skill from a bare task, then recite its rules" —
unfilled. Reciting rules is not a task a user phrases implicitly, so
the cell has no natural fixture. Recorded so a future reader sees it as
omitted on purpose rather than forgotten.

### Why `activation` and `discovery` both exist

They assert the same thing (the skill's self-announce marker appears)
over **opposite prompts**, and that is precisely the distinction the
suite is missing today:

- `activation` — explicit prompt, so a failure means the skill file is
  unreachable, malformed, or ignored.
- `discovery` — implicit prompt, so a failure means the trigger is too
  weak.

Collapsing them to one loses a question. Keep only activation and
triggering is never tested (today's gap). Keep only discovery and a red
test is ambiguous — weak trigger, or broken file? Because both are
generated by the runner from the *same* fixture field (the skill name),
keeping both costs a fixture author nothing.

### What a new skill is expected to carry

- **`integration`** — at least one. The end-to-end proof.
- **`enact`** — one per load-bearing behavior.
- **`playback`** — one per guardrail or absence path that produces no
  artefact (a refusal, a stop-with-error, a safety posture).
- **`activation`** / **`discovery`** — free. The runner generates them
  from the skill name, so every skill gets them without authoring
  work.

## Requirements

Two audiences: the person running `just resources::verify-skills`,
whose surface is which tests pass and what a failure tells them; and
the author (human or agent) adding a skill, whose surface is the
documented taxonomy and the small amount a fixture must state.

### Test-suite experience

- Running the suite exercises both axes per skill: that the skill
  states its contract correctly, and that it fires and performs from a
  bare task.
- **Implicit-prompt tests name no skill and no path.** The agent must
  select the skill from what its harness already surfaces. A prompt
  mentioning the skill's name, its marker text, or a `SKILL.md` path is
  not an implicit test.
- **Explicit-prompt tests are constructed with the correct path for
  the agent under test** — including codex, which six fixtures
  currently omit. No fixture hand-writes a skill path.
- When an explicit test passes and its implicit counterpart fails, the
  fault is localised to triggering rather than content, with no
  bisection.
- Every skill has implicit coverage — including the two whose behavior
  produces no file (`writing-style`, `browser`).
- For a skill whose behavior lands as a **filesystem artefact**, the
  artefact is the proof: a no-op agent leaves nothing behind and fails.
- For a skill whose behavior is **prose in the reply**, the proof is
  the skill's own self-announce marker appearing though the prompt
  never asked for it, plus a judge on the prose. An agent that answers
  competently from general ability, never having loaded the skill,
  fails.
- A failing implicit test reads as a real signal about trigger
  strength, not as a test to loosen.

### Authoring experience

- A fixture states only what is specific to it: the skill it tests,
  the task, and what counts as correct. It carries no skill paths, no
  "load the skill from …" preamble, and no class metadata.
- The four test kinds are functions in the runner, named for the
  question each answers, so reading the runner tells a reader what a
  skill test can be.
- A run can be scoped to one kind, so "show me every implicit test" is
  answered by running it rather than by grepping.
- A fixture that supplies nothing a kind can verify fails as
  malformed, naming what was missing.
- `project.md` narrates the two axes, the kinds they compose to, the
  deliberately-empty cell, and what a new skill is expected to carry.
- No skill content changes. `SKILL.md` files are untouched; this
  feature moves fixtures, the runner, the Justfile, and docs.

## Test Strategy

Per `project.md`'s two layers:

- **`just test` (unit, load-bearing, §8 Test Gate).** The runner is
  bash with no unit-test surface; its own guards (malformed fixture,
  unknown kind) are enforced at run time as the missing-`prompt:` guard
  already is. This feature touches no Rust, so the gate stays green
  with no new unit test.
- **`just resources::verify-skills` (functional, user-driven,
  credit-costing).** Where the fixtures live. Per `project.md`
  "Functional tests are user-driven," the agent prepares fixtures and
  names the commands; running them is the user's call.

Because the runner now generates prompts, several checks are
**verifiable without spending credits** — worth doing first:

- The constructed explicit prompt for each agent contains that agent's
  own skill root (the codex-path bug is caught here).
- The constructed implicit prompt contains no skill name, no marker
  text, and no `SKILL.md` path.
- A fixture missing required fields fails before any agent is invoked.
- `--kind <name>` selects the right subset; an unknown kind exits
  non-zero.

Success criteria — coverage per skill after this feature:

| Skill | playback | enact | activation / discovery | integration |
|---|---|---|---|---|
| `kdevkit` | dev-loop | — | generated | planning, closure, agents-md |
| `notes` | add-note, vault-selector | — | generated | notes, git-commit, topic-no-stub |
| `writing-style` | learning-loop | formatter | generated | *new* |
| `browser` | safety | — | generated | *new* (describe-only) |

The discriminating question for every implicit test: *could an agent
that never loaded the skill pass this?* For artefact skills, no — the
assert greps for files and content in the skill's specific shape. For
prose skills the marker is the guard: text the agent can only know from
the skill file, which the prompt never supplies.

## Design

**Rationale first.** Three alternatives were considered and rejected.

- **Strip the name and path from all 13 fixtures.** Conflates two
  failure modes in every test — a red fixture could mean bad content
  *or* failed triggering — so every failure needs manual bisection, and
  the explicit-prompt tests lose the isolation that is their whole
  purpose.
- **Declare a `class:` field per fixture and have the runner interpret
  it.** This was the previous revision of this plan. Rejected: it
  splits the taxonomy across 15 files (data) plus the runner
  (behavior), so the fixtures carry metadata *about* tests rather than
  test content, and the vocabulary still has to be learned from a doc
  rather than read off the code. Putting the kinds in the runner as
  functions makes them executable documentation.
- **Infer the kind from a fixture's shape** (has `assert` →
  behavioral). Rejected: shape does not determine purpose — a judge
  fixture can be playback, enact, or integration — so inference would
  be wrong about as often as right.

The chosen shape follows the runner's existing grain. `tool_invoke` is
already the single indirection point for per-agent CLI differences;
per-agent *skill paths* belong beside it for the same reason. And the
canonical paths already exist twice — in `build-tool`'s `REGISTRY`
(`.claude/skills`, `.kiro/steering/skills`, `.codex/skills`) and
hand-copied into fixtures. The fixture copies are the drifted ones, so
they are what to delete.

### Fixture format

A fixture states only what is specific to it:

- `skill:` — which skill is under test (new; drives prompt
  construction for every kind).
- `task:` — the work stated plainly, with no mention of the skill or
  its path (replaces today's `prompt:`). The runner wraps it in either
  the explicit or implicit envelope.
- `expect_substr:` / `expected_narrative:` / `--- setup ---` /
  `--- assert ---` — unchanged; what counts as correct.
- `tools:` — unchanged.

The `skill:` field is what makes generated activation and discovery
tests possible, and what lets the runner assemble the right path per
agent. Retiring the hand-written `Load the <skill> from <path>`
preamble is what fixes the codex drift.

### Runner responsibilities

1. **Per-agent skill roots.** A `skill_path <tool> <skill>` function
   beside `tool_invoke`, returning `~/.claude/skills/<skill>/SKILL.md`,
   `~/.kiro/steering/skills/<skill>/SKILL.md`, or
   `~/.codex/skills/<skill>/SKILL.md`. One place to change when a
   harness moves its root, and it cannot disagree with itself per
   fixture.

2. **Prompt construction, two envelopes.** *Explicit* prepends a load
   instruction naming the skill and that agent's path, plus the
   self-announce request where the kind needs a marker. *Implicit*
   passes the task essentially bare — no skill name, no path, no marker
   request — so the marker can only appear if the skill fired on its
   own.

3. **One function per kind** — `run_activation`, `run_discovery`,
   `run_playback`, `run_enact`, `run_integration` — each composing an
   envelope with an assertion strategy over the existing
   `assert_response` / `assert_behavioral` primitives. Reading these
   five names in the runner is how a future author learns what a skill
   test can be.

4. **Two enact strategies.** Artefact skills assert against the seeded
   workdir; prose skills (`writing-style`, `browser`) have no artefact,
   so they assert the self-emergent marker plus a judge narrative.
   Chosen from which assertion the fixture supplies — an `--- assert ---`
   block means artefact, otherwise judge — not from a declared field.

5. **`--kind <name>` filter**, composing with the existing positional
   name selector and `--tools`; unknown kind exits non-zero. The
   runner's header comment (its `--help`, extracted by the existing
   `awk`) gains the axes and the five kinds, so `--help` is itself a
   source of truth.

A note on the runner's existing constraint: behavioral and response
verification are **mutually exclusive** in the fixture loop — a fixture
with setup/assert blocks never has its `expect_substr:` evaluated. That
is why artefact-based kinds rely on the assert alone, and why the
`When done print [<skill>] applies` line in all six behavioral prompts
today is dead text to delete rather than logic to preserve.

### Surface and docs

Add `just resources::verify-skills-kind <kind> [agent]`, following
`verify-skills-one`'s shape (`[no-cd]`, one-liner over the runner,
agent selector), carrying the same `[confirm]`-and-credits caveat since
a kind spans many fixtures. Then narrate the design in `project.md`
Testing — the two axes, the five kinds, the empty cell, and what a new
skill carries — and register the new verb in `project.md`'s
Architecture entrypoints list.

## Decision Log

- **Taxonomy lives in the runner, not in fixture metadata
  (2026-07-29).** Supersedes the previous revision's per-fixture
  `class:` field. A fixture carries only skill + task + assertions; the
  runner owns paths, prompt envelopes, and the kinds as functions.
  Rationale: metadata-in-fixtures splits data from behavior across 15
  files and still requires learning a vocabulary from a doc, whereas
  five named functions in one file are executable documentation. It
  also removes the duplicated skill paths that had already drifted.
- **Two axes, five named kinds (2026-07-29).** *Explicit vs implicit*
  reach × *playback vs enact* verification. `integration` is named as
  the composition enact × implicit because that end-to-end pair is the
  one worth running. *playback × implicit* is deliberately empty —
  reciting rules is not a task phrased implicitly.
- **`activation` and `discovery` stay separate (2026-07-29).** The
  proposal assumed they were the same test. They share an assertion but
  invert the prompt, which is exactly the distinction the suite lacks:
  activation failing means an unreachable or malformed skill file,
  discovery failing means a weak trigger. Both are generated by the
  runner from the `skill:` field, so keeping both costs nothing.
- **Marker is the proof for prose-skill implicit tests (2026-07-29).**
  `writing-style` and `browser` produce no artefact, so a bare-task
  judge alone could be passed by a capable agent that never loaded the
  skill. The self-emergent marker is the one signal only a loaded skill
  can produce.
- **No marker assertion where an artefact exists (2026-07-29).** The
  runner routes setup/assert fixtures to `assert_behavioral` and never
  evaluates their `expect_substr:`, so a marker there is inert. The
  artefact is the proof; the dead `print [<skill>] applies` lines are
  deleted.
- **Clash detection out of scope (2026-07-28).** Probing skill
  collisions needs deliberately near-boundary prompts — a distinct
  design with its own flakiness profile. Per the user, not something to
  take on now, and not filed as backlog.
